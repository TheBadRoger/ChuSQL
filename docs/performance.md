## 测试方法与复现

`benchmark/` 中的应用名为 `benchmark4csql`。它启动真实 `chusql-server`，通过本机 TCP 使用共享客户端协议，服务端调用 Rust 存储，覆盖从客户端到真实存储的完整链路。每次运行创建独立临时数据库，结束后停止服务并清理数据；SQL、结果校验或并发请求失败都会让运行失败。

### 构建与运行

先在 `chusql-core/storage/` 执行 `cargo build --release`，生成优化后的存储动态库。再进入 `benchmark/`，在 PowerShell 中构建并运行：

```powershell
$repoRoot = (Resolve-Path '..').Path
$benchmarkTemp = Join-Path $repoRoot 'logs/benchmark-tmp'
New-Item -ItemType Directory -Force -Path $benchmarkTemp | Out-Null
$env:TEMP = $benchmarkTemp
$env:TMP = $benchmarkTemp
$env:PATH = (Join-Path $repoRoot 'chusql-core/storage/target/release') + ';' + $env:PATH
$env:GHC_CHARENC = 'UTF-8'
stack build chusql-core-model chusql-core-engine chusql-interface chusql-server chusql-bootstrap benchmark4csql --force-dirty --ghc-options=-O2
stack exec -- benchmark4csql 10000 50000
```

Linux 下用 `LD_LIBRARY_PATH` 指向 release 存储目录。两个参数分别是用户数和订单数，默认 10,000 / 50,000，每个至少 100。

### 采样与结果校验

读取场景先预热一次，再采样七次，记录均值、p50、p95、最大延迟与请求数/秒。p95 取最近秩，七次采样中 p95 等于最大值，适合比较本次场景，不构成稳定的生产尾延迟。

并发场景使用独立的已认证 TCP 会话，1、4、8 个客户端各执行 100 次点查并同步开始；吞吐按整个并发阶段的墙上耗时计算，连接与登录不计入该阶段。

加载主表时每条 INSERT 包含 500 行。另测逐条持久化提交、200 条 INSERT 的单次事务提交、更新、删除和事务回滚。写入保留 WAL、数据刷盘和检查点路径，持久化保持开启。

查询耗时包含 TCP、SQL 解析、语义检查、引擎执行和响应解码，不含 UI 渲染。读测试主要校验结果行数，加载 COUNT、并发点查值和回滚后值另行校验。

## 实测环境

- 测量日期：2026-10-05，Asia/Shanghai。
- CPU：AMD Ryzen 7 7840H，8 核 / 16 逻辑处理器。
- 可见物理内存：31.2 GiB。
- 系统：Windows 11 专业版，10.0.26200。
- 数据目录：D 盘 NTFS 上仓库 `logs/` 的临时子目录；未测存储设备裸吞吐。
- 编译：GHC 9.10.3，Haskell 本地包 `-O2`，Rust release 动态库。
- 规模：10,000 用户、50,000 订单、5,000 条 512 字节字符串宽行；订单按用户循环分配，年龄按 100 个值循环分布。

## 性能测试结果

下表是 2026-10-05 的基准样本。完整运行通过结果校验后输出 `BENCHMARK_OK`，原始日志为本机 `logs/benchmark-performance.log`。

启动、引导、认证及创建基准库合计 0.62 秒。纯 TCP Ping 200 次平均 0.100 ms，schema catalog 200 次平均 0.267 ms。主键点查另外连续执行 100 次，平均 0.300 ms，100/100 命中。

## 事务基准

同日、同一台机器、10,000 用户 / 50,000 订单规模的独立测量，结果校验通过。日志为本机 `logs/repair-txn-performance.log`，与上面的场景不是同一次采样。

| 指标                    | 耗时（ms） |
| ----------------------- | ---------: |
| 200 次独立持久化 INSERT |    1,134.7 |
| 事务 200 条 INSERT 总计 |    687.355 |
| BEGIN                   |    269.806 |
| 事务内 200 条 INSERT    |     41.129 |
| COMMIT                  |    376.345 |

事务写入约 290.97 行/秒。BEGIN 与 COMMIT 合计约占总耗时的 94%，COMMIT 还包含差分、冲突检查和持久化，不能全部归因于快照。提交跳过未修改的表，整数键差分使用 `IntMap` / `IntSet`，冲突检查与操作生成复用差分。

## 瓶颈与使用范围

| 样本中的观察           | 解读与后续测量方向                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| 整库事务快照成本高     | 同一提交点复用最近的快照版本；变化后仍读整库，可分别测缓存命中、传输、修改表比较与刷盘        |
| 不同外层绑定重复扫描   | 20 个不同绑定的相关 EXISTS 在事务基准运行中均值 2,135.218 ms；该样本反映测量时的执行路径      |
| 大结果与排序有全量成本 | 扫描包含解码、执行、TCP JSON；完整排序后 LIMIT，可分别评估 Top-K、分页和流式返回             |
| 批量提交摊薄固定开销   | 场景的数据库大小和已打开表数量不同，不构成严格单变量对照；刷盘优化仍须验证恢复              |
| 读并发低于线性扩展     | 8 客户端吞吐约为 1 客户端的 4.8 倍；混合读写与并发写尚未测量                                 |

> [!IMPORTANT]
> 这是单机回环、以热缓存为主、管理员身份的基准样本，不是生产容量承诺。远程网络、权限目录规模、冷缓存、内存峰值、崩溃恢复耗时和并发写冲突尚未测量；七次读采样与单次写测量不足以建立统计置信区间。

后续比较应保持机器、数据分布和构建参数一致，多次独立运行，并记录各阶段时间与分配量。
